# langchain-direct-study

Does LangChain used directly (its chains and runnables API, no graph
layer) land in the same place as a native loop on the identical task
suite, or does the abstraction tax differ from the graph framework's?
This is the paired-study sequel to
[JesunAhmadUshno/langgraph-vs-native-study](https://github.com/JesunAhmadUshno/langgraph-vs-native-study):
same 12 tasks, same deterministic scripted policy, same native control,
same axes, so the two studies compose. Hypotheses and verdict rules were
frozen in [PREREGISTRATION.md](PREREGISTRATION.md) as the first content
commit, before any measured run.

## Verdicts

- **H1, task success equivalence: CONFIRMED.** pass^1 is 0.979 in both
  arms. All 12 paired per-task differences are exactly 0.000; the 90
  percent interval is [0.000, 0.000], inside the frozen plus or minus
  0.05 margin.
- **H2, abstraction tax on wall time: REFUTED.** The registered tax
  hypothesis (median wall ratio above 1.10) fails because the measured
  ratio is 0.459, under the frozen 1.00 no-tax line. LangChain direct
  is faster than this native implementation on this suite, not slower:
  median 0.398 s versus 0.869 s per run, faster in 96 of 96 paired
  runs.
- **H3, exactly-once recovery in both arms: CONFIRMED.** 48 of 48 fault
  runs passed in each arm under SIGKILL at the registered kill points,
  with zero duplicated effects anywhere. Exactly-once came from the
  shared idempotency discipline for the third time (native, LangGraph,
  now LangChain direct).

## Beside the LangGraph study

Same suite, same policy, same native design, same machine. The
LangGraph column is the sibling study's published result; its native
column was a separate run of the identical native implementation, so
small native wall differences between the two studies are run-to-run
variation on a shared machine.

| Measure | Native (this study) | LangChain direct | LangGraph (sibling, published) |
|---|---|---|---|
| Overall pass^1 | 0.979 | 0.979 | 0.979 |
| Median wall seconds per run | 0.869 | 0.398 | 0.293 |
| Wall ratio to native | 1.000 | 0.459 | 0.299 |
| Durable state bytes per run, median | 16,384 | 8,192 | 36,864 |
| Recovery (48 fault runs) | 48 of 48 | 48 of 48 | 48 of 48 |
| Recomputed steps, median | 0.5 | 0.5 | 1.0 |

Read plainly: on success and on recovery the three arms are
indistinguishable, because the scripted policy and the idempotency
discipline, not the framework, decide those axes. On wall time both
framework arms beat this native implementation, LangGraph by more than
LangChain direct; that cross-framework gap is descriptive only, since
each ratio was measured against a different native run on a shared
machine, and the native arm's synchronous commit policy is a free
parameter (a WAL-mode native variant is untested, see ROADMAP.md).
On durable state, LangChain direct is the smallest of the three: its
single-row state store is 8,192 bytes against the native event log's
16,384 and LangGraph's checkpoint store's 36,864.

## Design in one paragraph

The shared core (fixtures, policy, tools, executor, scoring) and the
native arm are imported verbatim from the sibling repository; the suite
refuses to run unless the fixtures sha256 equals the sibling's
published hash. The LangChain arm sequences work as a RunnableSequence
of three RunnableLambda stages (load state, run one executor step,
persist state) from langchain-core 1.7.6, invoked once per step.
langchain-core has no checkpointer, so the persist stage writes the
full state dict to the arm's own SQLite store after every step, the
same commit-per-step cadence as both sibling arms (the mapping is
registered in PREREGISTRATION.md and DECISIONS.md D4). langchain 1.4.9
installs langgraph as a transitive dependency; the arm never imports
it, and a test proves it. The prompt-injection axis stays deferred,
exactly as the sibling deferred it: a scripted policy does not read
tool output as instructions, so attack success is undefined, not zero
(DECISIONS.md D2).

## Reproduce

```bash
python -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m pytest -q            # unit, smoke and reproduction tests
.venv/bin/python -m study.run_suite      # the registered suite, one pass
.venv/bin/python -m study.analyze        # RESULTS.md, summary.json, checksums
```

Pins: langchain 1.4.9, langchain-core 1.7.6, Python 3.12.3. The pins
are part of the result; a version bump is a new measurement.

## Limitations

- The policy is scripted, so no reasoning is measured. The research
  object is the orchestration layer only; the real-model run is the
  Deep pass in ROADMAP.md.
- Wall time is implementation-sensitive. The native arm is one
  competent design point, not "the" native approach, and its commit
  policy is disclosed wherever the ratio is reported.
- The H1 interval is degenerate (every paired difference is exactly
  0), which is what a shared deterministic policy produces. The test
  rules out orchestration-caused success loss on these fixtures; it
  says nothing about behaviour with a model in the loop.
- One machine, one suite pass, small deterministic fixtures. Scores
  here are not comparable to any published leaderboard.

## Why this matters

Framework choice is a recurring, expensive decision for small AI
teams, and it is usually made on fashion, conference talks, or a
teammate's habit. Paired measurements on identical tasks are how it
stops being a matter of fashion: freeze the question, run both arms
against the same work, publish the numbers either way. This study and
its sibling now give a small team three measured data points on the
same suite (native, LangChain direct, LangGraph) covering the axes
that actually bite in production: whether tasks succeed, what a run
costs in time and durable state, and whether a killed process resumes
without duplicating side effects.
